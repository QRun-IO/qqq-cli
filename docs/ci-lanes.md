# CI lanes for the qqq CLI

## What runs today

`.circleci/config.yml` is the qqq-orb setup stub; `.qqq-ci.yml` selects the orb's `cli` profile (orb 0.8,
read from `qqq-orb` at v0.8.32, identical to `develop`). That profile generates one job,
`qqq-orb/cli_verify_publish`, on **Linux, `cimg/node:22.12`**:

1. `npm ci`
2. `npm run generate`, then `git diff --exit-code -- packages/ui-api-client/src/schema.ts`
3. `npm run build`, `npm test`
4. a Prism smoke: `prism mock` on the merged document, `GET /qqq/v1/version` and `/metaData/authentication`
5. on a tag `v<client version>` with `publish.release: true`: `npm publish --tag rc` of
   `@qrun-io/qqq-ui-api-client`, `@qrun-io/qqq-ui-api-conformance` and `@qrun-io/qqq-cli` to GitHub Packages

Checked on 2026-10-31 by running the orb's own `cli_verify.sh` in Docker on the release branch, plus
`npm run prepublishOnly` and `npm run lint`:

| Image | Result |
|---|---|
| `node:20-bookworm-slim` (Node 20.20.2) | all green |
| `cimg/node:22.12` (the orb's image) | **fails**: two tests in `packages/cli/src/test/prompt.test.ts` (Ctrl-D and Ctrl-C at a question) end with "Promise resolution is still pending but the event loop has already resolved". They pass on Node 20.20, 22.23 and 24.22; it is a readline behaviour of 22.12. The fix belongs in the test or `prompt.ts`, or the orb image moves to a current 22.x. |

Gaps in the profile, to fix in the orb:

- **`@qrun-io/qqq-core` is not published.** `@qrun-io/qqq-cli` depends on it, so the CLI package the
  orb publishes cannot be installed until core is published by hand (`scripts/release.mjs` prints the
  command). Add it to `cli_publish.sh`, before the CLI, with the same destination check.
- **No lint.** Commit 7f1ad5e added `prepublishOnly` and `lint` for the orb's node profile, but this repo
  uses the `cli` profile, which runs neither. `npm run lint` now also checks that the release versions
  agree; it should gate a publish.
- **One Node version.** The packages declare `engines.node >=20`; the orb tests only 22.12. Until this
  release, `npm test` failed on Node 20 (the quoted test glob needs Node 21+), and nothing noticed.
- **No macOS or Windows.** The keyring has three platform paths (Keychain, Secret Service, DPAPI through
  PowerShell), the binaries are built for five targets, and only Linux runs anything.
- **`operations.ts` drift** is regenerated by `npm run generate` but not diffed; add it to the
  `git diff --exit-code` line (`scripts/release.mjs` already checks both).
- The TUI (`npm run test:tui`, `typecheck:tui`) needs Bun, which the image does not have.

## Proposal: platform lanes

Two lanes, both on pull requests and tags: **macOS arm64** (tier 1 in the design, Keychain) and
**Windows x64** (tier 2, DPAPI, PowerShell completion, the cross-compiled `.exe` actually run). Each
installs Node 20 and Bun 1.4.4, runs build, test and lint, builds the binary for its own platform with
`scripts/build-binaries.mjs --host` and smoke-runs it. Linux arm64 and musl can be added the same way
later (`arm.medium` machine executor, `node:20-alpine`).

### Option A (recommended): an orb change

The `cli` profile is the one place CLI CI is defined, so the lanes belong there. Changes in `qqq-orb`:

1. a new job `src/jobs/cli_platform.yml` (the job below, with the executors inlined as parameters);
2. `cli_template` in `src/scripts/generate_pipeline.py` appends one `qqq-orb/cli_platform` job per
   entry of a new optional manifest key, and makes `cli_verify_publish` require them on tags (sketch;
   the manifest validation in `generate_pipeline.py` has to accept the key):

   ```python
   platforms = config.get("platforms", [])          # validated: subset of ("macos-arm64", "windows-x64")
   jobs = [{"qqq-orb/cli_platform": {"name": f"cli-{p}", "platform": p, "filters": filters}} for p in platforms]
   options["requires"] = [f"cli-{p}" for p in platforms] if publish else []
   jobs.append({"qqq-orb/cli_verify_publish": options})
   ```
3. `cli_verify.sh`: `npm run lint`, and `operations.ts` in the drift check; `cli_publish.sh`: publish
   `@qrun-io/qqq-core`; the image to a current `cimg/node:22.x`, plus a Node 20 run of `npm test`.

Then this repository opts in with two lines and no change to `.circleci/config.yml`:

```yaml
# .qqq-ci.yml
platforms: [macos-arm64, windows-x64]
```

### Option B: a second pipeline in this repository

If the orb change has to wait: CircleCI projects on the GitHub App integration can have more than one
pipeline, each with its own config file (Project Settings, Pipelines, "Add pipeline", config path
`.circleci/platforms.yml`, trigger on pushes and tags). The orb's setup pipeline stays as it is. The file
below validates with `circleci config validate` (CLI 1.13.0); it has not run on CircleCI, and the macOS
and Windows resource classes need the plan to include them. This option was not applied: the
repository's `.circleci/config.yml` is unchanged and still only the orb stub.

```yaml
version: 2.1

executors:
  macos-arm64:
    macos:
      xcode: 16.4.0
    resource_class: m4pro.medium
  windows-x64:
    machine:
      image: windows-server-2022-gui:current
    resource_class: windows.medium
    shell: bash.exe

jobs:
  cli_platform:
    parameters:
      platform:
        type: executor
      binary:
        type: string
    executor: << parameters.platform >>
    environment:
      BUN_VERSION: 1.4.4
      NODE_VERSION: 20.20.2
    steps:
      - checkout
      - run:
          name: Node and Bun
          command: |
            if [[ "$OSTYPE" == darwin* ]]; then
              brew install node@20 >/dev/null && echo 'export PATH="$(brew --prefix node@20)/bin:$PATH"' >> "$BASH_ENV"
              curl -fsSL https://bun.sh/install | bash -s "bun-v$BUN_VERSION"
              echo 'export PATH="$HOME/.bun/bin:$PATH"' >> "$BASH_ENV"
            else
              nvm install "$NODE_VERSION" && nvm use "$NODE_VERSION"
              powershell.exe -NoProfile -Command "\$env:BUN_INSTALL='C:\bun'; & ([scriptblock]::Create((irm https://bun.sh/install.ps1))) -Version $BUN_VERSION"
              echo 'export PATH="/c/bun/bin:$PATH"' >> "$BASH_ENV"
            fi
      - run: node --version && bun --version
      - run: npm ci
      - run: npm run build
      - run: npm test
      - run: npm run lint
      - run:
          name: Binary for this platform
          command: node scripts/build-binaries.mjs --no-build --host
      - run:
          name: Binary smoke
          command: |
            ./dist/<< parameters.binary >> --version
            ./dist/<< parameters.binary >> __complete -- ta | grep -q table
            ./dist/<< parameters.binary >> completion pwsh > /dev/null
            QQQ_CONFIG_DIR="$PWD/.smoke" ./dist/<< parameters.binary >> config profile list
      - store_artifacts:
          path: dist

workflows:
  platforms:
    jobs:
      - cli_platform:
          name: macos-arm64
          platform: macos-arm64
          binary: qqq-darwin-arm64
      - cli_platform:
          name: windows-x64
          platform: windows-x64
          binary: qqq-windows-x64.exe
```

Notes on the YAML: Windows runs steps in Git Bash (`shell: bash.exe`), so the same commands work on
both lanes; `nvm` comes with the Windows image; `QQQ_CONFIG_DIR` keeps the smoke away from the agent's
profile. A Keychain round trip (`qqq login` against a Prism mock with `QQQ_EXTENSION_CHECK=off`, then
`logout`) is the next step for the macOS lane; on Windows the DPAPI store is covered by the kernel's unit
tests only.
